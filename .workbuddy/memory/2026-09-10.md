## ★ 关键结论：Safari（含 iOS）不支持 bookmarks API —— 书签同步在 Safari 全平台不可用
- 查证来源：Apple 官方论坛工程师回复（"It is not currently supported in Safari."）、MDN 兼容表（Safari / Safari on iOS 均 = No support）、多篇移植实测（"history, browsingData, bookmarks, topSites, sessions — absent wholesale"）、Bookmark UniSync 架构自述。
- 根因：Apple 2011 年移除 Safari 书签公开 API；2020 年引入 WebExtensions 时未实现 bookmarks；至今（Safari 26）仍不支持。苹果以隐私为由不允许扩展读写书签。
- 对本项目的影响（已核对源码）：`src/sync.js` 核心依赖 `api.bookmarks.getTree/getChildren/create/update/move/remove`；`src/lib/ext.js` 为 `globalThis.chrome ?? globalThis.browser`，**无 feature-detect 降级**。Safari 上 `api.bookmarks` 为 `undefined` → `getTree()` 抛 TypeError → 同步必失败（`src/background.js` 的 try/catch 会写入 "失败: ..."）。
- popup（`src/App.vue`）不直接调 bookmarks，故 UI 能渲染、登录可成功，但「立即同步」必失败。即 Safari 上只有一个空壳。
- **纠正**：上文「兼容性确认：Safari Resources 与 Chrome 扩展」一节中"bookmarks 在 Safari 可用、仅细节差异、代码可直接跑"的说法**错误**，以本节为准。
- iOS 额外门槛（即便 API 支持也挡着）：iOS Safari 扩展无法侧载，只能经 App Store 分发（开发期用 Xcode 装真机，需开发者账号）；iOS 不支持 webRequest / contextMenus / windows.create|remove|update。且 iOS 上所有浏览器均为 WebKit 强制内核，Chrome/Edge 同样不能装扩展、不能访问书签 → iOS 上"用浏览器扩展同步书签"整条路不通。
- Safari 桌面若要书签同步，唯一正规路径：原生 macOS App 直接读 Safari `Bookmarks.plist`（需 Full Disk Access 用户授权），且**无法上架 App Store**（Apple 同样禁止 App 访问书签）；iOS 侧 Safari 书签走 iCloud，第三方无法直接读写。参考产品 Bookmark UniSync 即此架构（macOS App 官网分发 + iPhone 靠 iCloud 中转）。

## ★★ 出路：Safari 书签同步改由「原生 macOS App」执行（扩展路线确认是死路）
- 原理：macOS 上 Safari 书签就是明文文件 `~/Library/Safari/Bookmarks.plist`（binary plist），**原生 App 可直接读写**。苹果卡的是「扩展 API」这一层，不是文件本身。
- 本机实测（2026-09-10）：文件存在，**4.78 MB**，mtime 2026-09-08；`plutil -p` 报 "you don't have permission to view it" → 证实受 TCC 保护，需 **Full Disk Access**。`SafariBookmarksSyncAgent` 正在运行 → **iCloud 书签同步已开启**。
- 权限硬约束（Apple 官方论坛开发者确认）：**Full Disk Access 不会解除 App Sandbox** —— 沙盒 App 即使被授予 FDA 仍读不到 `~/Library/Safari`；且 FDA 本身不是一个 entitlement，只能在商店外分发。因此必须：macOS (App) target **关闭 App Sandbox**（当前工程 `ENABLE_APP_SANDBOX = YES`，4 个 target 全开，需把 App target 改 NO）+ 用户手动授予「完全磁盘访问」。代价：不能上架 Mac App Store（个人使用无影响）。
- plist 结构（业界已知）：`Children` / `WebBookmarkType`(WebBookmarkTypeLeaf|WebBookmarkTypeList) / `URLString` / `URIDictionary.title` / `WebBookmarkUUID` / `ReadingList`。
- 现成参考实现：BookMacster、Alfred Bookmarks workflow、`safari-bookmarks-cli`、`safari-bookmarks-mcp`（PyPI，`uvx safari-bookmarks-mcp list` 可验证）。
- 风险：iCloud 同步开启时**写** plist 可能被 sync agent 锁定 / 产生冲突 → 建议先做「Safari → 云」**单向只读**，写回后置并加冲突保护。
- 工程信息：bundle id `catnuko.bookmark-sync`；targets = bookmark-sync (macOS/iOS) + bookmark-sync Extension (macOS/iOS)；无 .entitlements 文件（沙盒走 build setting）。
- iOS：确认无解 —— 第三方 App/扩展均不能读 Safari 书签，iCloud 是唯一途径。

## ★ 同步协议改版：快照 + 墓碑（并集合并），验证收敛 {C1,C2,N}（agent 执行）
- 用户问题：三端初始 {C1,C2,A}，A 机删除书签 A、B 机新增书签 N，问 C 机同步后最终状态能否为 {C1,C2,N}。原「先拉后推镜像」方案会互吞（C 拉 A 的删除 → 丢 N；或 N 推回 → 复活 A）。
- 方案：**快照 + 墓碑 + 并集合并**。新增=并集（任一设备有而服务端没有的保留）；删除=墓碑传播（`bsync_tombstones` 表，主键 (user_id,url)，删除过该 URL 的任何设备同步时都删它，且不被其他设备复活）；重加=原删除设备重新推同一 URL 时清除**自己**的墓碑（`device` 字段标记来源，首写者获胜）。设备用持久随机 `deviceId`（chrome.storage.local）。
- 数据库改动（`supabase/migrations/0005_tombstones.sql`，新增迁移）：`bsync_tombstones` 表（RLS + 上限 2000 条）；重写 `bsync_snapshot_push(p_data, p_tombstones, p_device)`：清自己墓碑 → 合并墓碑 → 墓碑过滤后配额检查 → 写入过滤后快照 → security definer `bsync_touch_used` 记账（带 `auth.uid() is distinct from p_user` 防越权改他人 used_bytes）；`bsync_snapshot_pull()` 返回 bookmarks + tombstones。注意：本迁移开头 `drop function bsync_snapshot_push(jsonb)` 会 cascade 掉 0004 的旧签名，需按顺序执行 0001→0005。
- 客户端改动：`src/sync.js` 重写 runSync = 拉取 → 并集合并应用（applySnapshot：墓碑删本地、服务端新书签补建、被墓碑的 URL 跳过不复活）→ 推送本地树+本地墓碑+deviceId；`getDeviceId()` 生成持久随机 ID；`background.js` 监听 `onRemoved`（记录墓碑）/`onCreated`（清除墓碑）。
- 本地验证（真实 Postgres 16 + 完整 5 个迁移 + setup.sql 复刻 Supabase 权限）：场景全部通过 —— [2-check] A 删 A 后服务端={C1,C2}+墓碑[A]；[4] **C 拉取 = bookmarks{C1,C2,N} + tombstone{A}（达成目标状态）**；[5] 原删除设备 A 重加 A → A 复活且墓碑清空；[6] 非删除设备 C 重加 A → 被墓碑过滤（粘性删除）；[8] 未登录调用抛 not authenticated（预期）。psql 退出码 3 仅为最后一个预期报错触发 ON_ERROR_STOP。
