# Firefox 同步后书签全挤在一处：树被打散的根因是「合并」模型

Firefox 同步完成后，几千条书签塌成了一片：原本分散在十几个文件夹里的书签挤进了同一个文件夹，新装 Firefox 的笔记本上某些子文件夹变成了空壳，或者整棵树被拍平挂到了根目录。同样的操作在 Chrome 上不会这样。这不是随机故障，Firefox 论坛里能翻到大量同一个题目的 thread。它的根因在数据模型，不在你的操作。

## 先把症状对上号

同步之后你看到的东西，落在三类里。分清是哪一类，才知道该往哪个方向查。

| 你看到的现象 | 属于哪一类 | 直接原因 |
|---|---|---|
| 十几棵树文件夹的内容全进了同一个文件夹 | 身份坍缩 | 两个本该不同的文件夹被判定成同一个 |
| 书签没丢，但全部平铺到根目录，层级消失 | 父链断裂 | 子节点指向的父 GUID 在本地解析失败，退到根 |
| 新笔记本上某个子文件夹变空，子书签散落在别处 | 层级未同步 | 文件夹记录本身没落地，只有子节点落地了 |
| 数量对得上，位置全错 | 重排未被采纳 | 排序键在合并中被判为旧版本丢弃 |

第二类和第四类最容易被误判成「书签丢了」。数量对得上说明数据没丢，只是归属关系错了。这一区分很重要——它决定了你是该找恢复方案，还是该修结构。

## 根因一：树节点对象不携带同步来源信息

要看懂这个，得知道 Firefox 书签树在代码里是怎么表示的。界面上你看到的那棵树，每个节点由 gecko-dev 里的 `BookmarkTreeNode` 表示。它对外暴露的是 `title`、`uri`、`level`、`index`、`parent` 这一类**展示层属性**。

关键在于它没有什么：

- 没有 `syncing` 字段。节点本身不知道自己是否已同步、是在哪台设备上创建的、由哪一方合并而来。
- 没有 `folderType`。文件夹的类型信息不在树节点上，要绕到 `nsIFolder` 接口才能取到。

而文件夹类型这件事在合并时非常关键。「工具栏」「书签栏」「其他书签」「移动设备书签」在 Firefox 内部是不同类型，各自有不同的存放约定和展示位置。一个节点如果带着类型，合并引擎在把它挂到新父节点下时可以选择兼容的落点；不带类型，就只能按 GUID 链硬接，接不上就退回根目录。

还有一个后果更隐蔽：Firefox 的同步状态是**集合级**的，不是节点级的。状态栏上那个「正在同步 / 已同步 / 同步出错」，描述的是整个书签集合这一次同步的结果，不是某一个文件夹。合并引擎在处理一条冲突记录时，没有一个字段可以写「这条来自 A 设备那条来自 B 设备，两边都改过」，所以它只能靠时间戳和内容去猜。

> 这解释了一件事：Firefox 同步出问题时，你没法从界面上看出是哪批记录出了问题，只能整体重来。这也是这类问题排查困难的主要原因。

## 根因二：合并模型与「本地/云端二分」的差别

同步引擎处理「本地和云端不一样」时，只有两种世界观。

| 维度 | 本地/云端二分 | 合并模型 |
|---|---|---|
| 数据身份 | 服务端给每条记录分配唯一 tag，本地记住自己有哪些 tag | 只靠 GUID 标识记录，两端共享同一套标识空间 |
| 看到云端有、本地没有 | 明确判定为「服务端新增」，直接新增 | 判定为「本地缺失」，先怀疑本地被删 |
| 判定依据 | tag 是否在本地已知集合里 | 时间戳、内容差异、父链能否解析 |
| 本地多出来的记录 | 明确的本地新增 | 可能是本地新增，也可能是合并失败的残留 |
| 结构信息 | 结构与条目同批下发 | 结构靠 GUID + 父链重建，链断即塌陷 |
| 并发改动 | 靠 base/remote 快照三方对比 | 靠合并 + 逻辑时钟裁决 |

Firefox Sync 属于右边这一列。这不是实现缺陷，两种模型都能工作，差别在遇到「结构被大改」时的表现。二分模型遇到服务端新增会无条件新增，因为它能区分「新增」和「删除」；合并模型不能，一旦本地状态被误判成「这里本来应该是空的」，引擎会把云端推来的结构当成冗余数据丢掉，节点就被挂到了根上。

Firefox 论坛里那类「3000 条书签的树被打散」的 thread，特征几乎一致：改名的改名、移动的移动、导入的导入，一次性大批量动结构，然后同步。这是合并模型最脆弱的输入。

## 根因三：结构靠父链重建，链断即塌陷

书签树的形状完全由「每个节点的 `parentId` 指向谁」决定。序列化时这是一组 ID 引用，反序列化时它必须逐级解析。

只要有一个引用解析不到，整棵子树的归属就悬空。工程上的处理通常只有两种：挂到根，或者挂到一个猜测的父节点。前者就是你看到的「全挤到根目录」，后者就是你看到的「全进了同一个文件夹」。

**「全进了同一个文件夹」通常是这条路径的结果**：两个文件夹记录在合并中被判为同一条（GUID 冲突或身份坍缩），引擎保留了其中一个，另一个的 `parentId` 变了，于是它下面所有子节点跟着换了家。子书签一条没少，只是全挂到了同一个父亲下面。

这个机制解释了最让人困惑的现象：**为什么数量完全对得上**。丢的是身份，不是数据。

## 四个自测动作

不用看文档，不用问人。四个动作能把上面四类症状区分开。

**测试一：数一遍节点总数。** 打开书签管理器，按地址栏搜一个你确信存在的关键词，看命中数。

- 总数和同步前一致 → 数据没丢，是结构问题，去测试二
- 总数明显变少 → 确实丢了，先看测试四

**测试二：找一个有子项的文件夹，改名，同步，看子项还在不在。** 子项全没了说明它按路径或标题匹配身份，不按节点身份。这一步单独就能测出路径字符串类实现。

**测试三：两台设备都离线，各自在同一个文件夹里加书签，然后同时联网。** 这是一次最小并发。

- 两边新增都在 → 有真正的合并能力
- 一边的三条整批消失 → 时间戳覆盖类实现，你丢的是刚加的东西

**测试四：换设备时只同步、不做任何本地改动。** 新设备上先不导入任何 HTML，直接登录同步，等它跑完。

- 树结构完整 → 云端结构是好的，问题出在合并环节
- 结构在这种情况下就散了 → 云端存的本来就是散的，本地那台只是忠实还原

测试四是四个里最有信息量的一个。它把「云端数据本身有问题」和「合并过程有问题」彻底分开了。绝大多数人从来没做过这一步，所以一直在这两者之间来回猜。

## 三类同步方案在这个场景下的差别

| 方案 | 结构完整性 | 并发安全性 | 换设备 |
|---|---|---|---|
| Firefox 原生同步 | 结构易在批量改动后坍缩 | 合并模型，复杂改动下不稳 | 同一账号即可，但结构可能已受损 |
| Chrome / Edge 原生同步 | 同步整个配置档，结构较稳 | 有 base/remote 快照与唯一 tag | 仅限同厂商，换浏览器不通 |
| 导出 HTML 手动迁移 | 空文件夹和纯中间层不被保留 | 无并发概念 | 每次手动，且要重新整理 |
| 按节点身份同步的第三方方案 | 改名只改 title，移动只改 parentId | 取决于是否用 CRDT | 登录即拉全树 |

关于第三行补一句具体的坑：HTML 书签文件不保存「空文件夹」和「只有子文件夹没有书签」的中间层。跨浏览器搬运一次，你就永久失去那些层级，而且没法手工补回来——因为它们在文件里就不存在。

## 动手修的顺序

顺序很重要，做反了会把仅存的正确结构也毁掉。

1. **立刻在所有设备上暂停同步。** 不暂停的话，塌陷的结构会继续传播，正确的副本也可能被覆盖。这一步最优先。
2. **导出一份 HTML 备份。** 从还没出问题的设备导。十秒钟的事。
3. **确认数据是否真的少了。** 做测试一。数量对得上就说明只是结构错乱，恢复是重排问题，不是找回问题。
4. **在一台设备上修好结构，让它成为源头。** 选一台数据最完整的设备作为权威副本，其余设备全部从它同步。
5. **修完再恢复同步。** 顺序反了会让你在两套错乱结构之间来回合并。

> 如果多台设备的结构已经各不相同，不要试图让它们互相合并。选一台修对，其余从它单向同步。合并两套错乱结构只会得到第三套错乱结构。

## BookmarkSync 的做法

我们同步的是节点身份，不是路径：每条书签带自己的 ID 和 `parentId`，改名只改 `title` 字段，移动只改子节点的 `parentId`。这两种操作都不会改变任何节点的身份，所以它们在同步里是最安全的两种变更。

排序也随节点一起走——每条书签带一个排序键，字典序排列、同值时用 UUID 破平。你在 A 设备拖动重排，B 设备跟着变，不需要整棵树重新下发。

并发用 CRDT 加逻辑时钟，收敛是确定性的：同一组输入在所有设备上得到同一个结果，不会这次这边赢、下次那边赢。

真实使用中 Firefox 书签确实是最容易出问题的场景之一，所以我们的自动整理功能只调移动和创建两个接口，从不调用删除。这个限制来自两次删数据事故的教训，不是技术上做不到。

## FAQ

### Firefox 同步后书签数量没变，但位置全乱了，数据还在吗？

在。丢的是节点的身份和归属，不是数据本身。这也是最容易被误判成「书签丢了」的情况。

区分方法很直接：在书签管理器里搜一个你确信存在的关键词，看命中数。数量对得上就说明数据还在，只是树结构错了，修法是重排而不是找回。

而且这种情况下通常不需要手工重排——只要云端还留有一份完整结构，换一台干净的设备登录同步就能拿到正确的树。

### 为什么把文件夹名字改回去，内容又出现了？

因为当时合并引擎没能按 GUID 认出这个节点，退而用标题匹配，改回去之后标题又对上了。

这是假象，不是修好了。判断依据是：改名的瞬间，那个书签的唯一标识有没有变。变了就说明它按标题或路径认节点，迟早还会塌。

### 同步出错时能不能查出是哪几条记录有问题？

很难。Firefox 的同步状态是集合级的，界面上显示的是整个书签集合这一次同步的结果，不是逐条的。

节点对象上不带同步来源信息，所以引擎在处理冲突时也没有地方记录「这条来自 A、那条来自 B，都改过」。这也是这类问题排查困难的直接原因——没有可观测的中间状态，只能整体重来。

### 换新设备时先导入 HTML 再同步，会不会更安全？

多数情况下反而更容易乱。两份来源会先合并，结构差异会被当成冲突来裁决，而不是被当成一份干净的数据直接采用。

想要的就是「不导入任何东西，登录，同步，等它跑完」。这样云端的结构原样落地，你看到的就是云端真实状态——好的坏的都能看清，坏的时候也知道坏在云端而不是本地。

### 有第三方自动整理工具会不会让情况更糟？

取决于它调哪些接口。只做移动和新建的整理不会丢数据，它改的只是 `parentId`，节点身份不变。会调用删除接口的实现有风险——删除一旦参与同步传播就不再是本机操作，别的设备也会跟着删。

在结构已经出问题的设备上跑自动整理，顺序很重要：先把结构修对，再整理。

### 从 Firefox 迁到别的浏览器，树能完整带过去吗？

按节点身份同步的方案可以，前提是对方也按节点身份接收。只有 Chrome 一条原生同步路的话，同步的是整个配置档，跨浏览器拿不到。

还有一件事要注意：无论走哪条路，手动导出 HTML 都不能当主力方案，因为空文件夹和纯中间层在 HTML 文件里不存在，导出一次就丢一次。
