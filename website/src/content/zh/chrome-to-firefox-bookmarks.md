# Chrome 书签迁移到 Firefox：会丢什么，以及怎么正确迁

从 Chrome 换到 Firefox，最省事的做法是导出 HTML 再导入。但几乎所有教程都只讲怎么点，不讲会丢什么——结果是导入完你才发现层级变了、多出空目录、书签散了一地。这篇先说清四个必然的限制，再给两条路径和验证方法。

## 迁移前要知道什么

### HTML 书签文件不保存空的中间层文件夹

这是最容易踩的一个坑，也是最容易被误认为 bug 的一个。HTML 书签格式在结构上无法表达「这个文件夹存在，但里面一条书签都没有，只有子文件夹」这种中间层。Chrome 里你可以建 `工作/前端/规范` 这样一条链，`规范` 下面只有子文件夹、没有书签。导出后这层就消失了，导入 Firefox 时你看到的是 `工作/前端` 直接挂着原本属于下一层的东西。

多出来的空目录同理：Chrome 里那些你随手建了又没用的空文件夹，导入后可能以奇怪的形式残留。**这是格式限制，不是工具做得差。** 任何基于 HTML 的迁移都绕不开。

> 判断你有没有中招：随便挑一个你记得是「三层以上、且中间层没有直接书签」的文件夹，在 Firefox 里数一下层级。少了一层就是被拍平了。

### Firefox Sync 是合并模型，没有「本地/账号」之分

这点是 Chrome 和 Firefox 最本质的差异，也是所有跨浏览器同步工具的难点所在。

Chrome 把书签树拆成两棵**平行子树**：本地子树和账号子树，靠每个根节点上的 `syncing` 字段区分。所以一个登录了 Google 账号的 Chrome，`getTree()` 返回的根下面可能同时挂着 6 个根：本地书签栏、本地其他书签、本地移动设备书签，加上账号书签栏、账号其他书签、账号移动设备书签。

Firefox 没有这套东西。Firefox 的 `BookmarkTreeNode` **既没有 `syncing` 字段，也没有 `folderType`**，只有一个固定的 `root________` 根，下面是四个内置文件夹：书签菜单、书签工具栏、其他书签、移动设备上的书签。Firefox Sync 的思路是把两边的书签**合并**成一份，而不是区分「哪部分属于账号、哪部分属于本机」。

直接后果是：**你没法在 Firefox 里拥有 3 个互相独立的账号根。** 任何声称能在 Firefox 里复刻 Chrome 三账号根结构的方案，都在某个环节做了妥协——通常是悄悄把东西并进了同一个文件夹。

### Chrome 的账号子树在 Firefox 端只能落到「其他书签」下

承接上面那条。既然 Firefox 端没有账号子树这个概念，Chrome 登录 Google 账号后同步过来的那部分书签，在 Firefox 端就没有对应的落点。唯一合理的去处是本地「其他书签」——也就是 Firefox 的 `unfiled_____`。

BookmarkSync 对这件事的处理是：根落地时**永远退回本地「其他书签」**，在它下面建一个同名文件夹装下整棵子树，绝不退到 Chrome 的账号子树里去。

> 为什么不退到账号子树？听起来那里更「对应」，但那是 Chrome 自动同步管理的，网页扩展往里写东西，等于把用户的书签上传到他的 Google 账号里。位置对上了，归属就错了。

这条行为有回归测试锁住，`tests/sync/crossBrowser.test.ts:157` 那组用例就是拿 Firefox 实测的根形状（无 `folderType`、无 `syncing`）跑一遍，验证账号子树的内容确实落在「其他书签」下的同名文件夹里。回归测试的意义就在这儿：这个行为不是「碰巧这样」，是被固定下来的约定。

### Firefox 的 `tags________` 不该被捕获

Firefox 有个内置书签文件夹叫 `tags________`，是浏览器用来内部管理书签标签的。它出现在书签树里，但它不是用户书签。

任何同步工具在扫描 Firefox 书签树时都应该跳过它。捕获了会怎样？会生成一批谁都不想要、删掉又立刻回来的幽灵节点——它们属于浏览器内部结构，Firefox 会重建。

## 两条迁移路径

| 对比项 | 原生方式：导出 HTML 再导入 | 跨浏览器同步工具 |
|---|---|---|
| 速度 | 一次性，十几分钟 | 装好后长期生效，新设备秒级初始化 |
| 空中间层文件夹 | **会丢**，格式本身不支持 | 保留，按节点身份同步 |
| 账号子树处理 | 无对应概念，整棵树混在一起 | 落到「其他书签」下的同名文件夹 |
| 需要手工整理 | 每次换设备都要重来 | 不需要 |
| 适合的场景 | 只换这一次浏览器 | 以后还要来回换 |

关键区分：**原生方式是「一次性搬家」，同步工具是「跨浏览器持续同步」。** 如果你这辈子只从 Chrome 换到 Firefox 这一次，之后再也不回来，原生方式更快、更安全、没有任何第三方能碰到你的书签数据，别用工具。

只有当你需要**多台设备、多种浏览器长期混用**时，工具的价值才存在——而且那个价值在于「持续」，不在「搬家」。

## 动手步骤

### 路径一：原生导入（只迁这一次）

1. 在 Chrome 里打开 `chrome://bookmarks`，右上角三点菜单选「导出书签」。
2. 存下来的 `.html` 文件先别急着导入 Chrome 那边。**打开它看一眼**：搜一个你记得是「中间层没有直接书签」的文件夹，如果搜不到，说明这层已经丢了，你知道会坏在哪里。
3. 装好 Firefox 后，菜单栏「书签」→「显示所有书签」，然后「导入和备份」→「从 HTML 文件导入」。
4. 选第 1 步那个文件。Firefox 会问导入到哪个文件夹，选「其他书签」——因为我们上面说了，Firefox 端没有账号子树的概念。
5. 导入完先别急着删 Chrome 里的书签，按下面「怎么验证」那节对一遍。

### 路径二：用 BookmarkSync 拉完整书签树

1. 在 Chrome 侧安装 BookmarkSync 扩展，登录任意一个账号。它会把当前书签树按节点身份（节点 ID + `parentId`）完整上传，空的中间层文件夹也作为节点保留。
2. 在 Firefox 侧安装同一个扩展，登录**同一个**账号。
3. 拉取完成后，Chrome 账号子树的内容会出现在 Firefox 的「其他书签」下的同名文件夹里。你不需要导 HTML，也不需要手动重新建层级。
4. 之后你在任意一边改文件夹名、移动位置，另一边跟着变。改文件夹名只改 `title` 字段，移动只改子节点的 `parentId`，节点 ID 从头到尾不变，所以结构不会塌。

BookmarkSync 支持 Chrome / Edge / Firefox。**Safari 暂时不支持。** 额度上免费档 500 条书签、1MB、1 个同步空间，Plus 10,000 条、20MB、3 个空间，Pro 不限条数、500MB、10 个空间。加密用 AES-GCM，服务端只存密文。

## 怎么验证迁移成功

导入完对一遍，比事后补救便宜得多。这四步按顺序做：

1. **对总数。** 在 Chrome 和 Firefox 两边分别数一下书签条数（不含文件夹）。对不上，先查是不是漏了一个根，或者空文件夹被当成了书签。
2. **验层级，而不是看数量。** 挑一个你有印象的三层嵌套文件夹，逐层点开确认层级还在。数量对但层级被拍平，是 HTML 迁移最典型的失败形态。
3. **查空目录。** 随便翻翻有没有你从没建过的空文件夹。多出来的空目录是 HTML 格式丢中间层时的残留，删掉即可，但它说明这次迁移有信息损失。
4. **试一次改名。** 挑一个有子项的文件夹改名，刷新另一侧。子项还在 → 结构是稳的。子项没了 → 那个工具存的是路径字符串，不是节点身份，长期一定会坏。这一步是整套判据里最灵敏的一下。

第 4 步尤其值得做，因为它测的不是「这次迁移成没成」，而是「以后每次改名会不会出事」。HTML 迁移只经得起一次测试，同步方案才经得起第二次。

## FAQ

### Chrome 导入 Firefox 后少了几个文件夹，是丢数据了吗？

多半是空的中间层文件夹被拍平了。HTML 书签格式在结构上无法表达「只有子文件夹、没有书签」这种中间层，导出时就丢了。这是格式限制，换任何工具走 HTML 都会遇到，不是某个工具的 bug。真正的书签数据（带 URL 的那些）不会因为这个原因丢。

### Firefox 能不能像 Chrome 一样有多个独立的账号书签根？

不能，这是架构差异不是功能缺失。Chrome 的书签树分成平行的本地子树和账号子树，靠根节点上的 `syncing` 字段区分；而 Firefox 的 `BookmarkTreeNode` 没有 `syncing` 字段、没有 `folderType`，Sync 采用合并模型把两边合成一份。所以在 Firefox 端，Chrome 账号子树的内容只能落到本地的「其他书签」下面，这是模型决定的。

### 迁移到 Firefox 后，Chrome 那边还需要留着吗？

建议先留着，等你按上面「怎么验证」那四步对完再决定。HTML 导出只花一分钟，但它不能保住空的中间层文件夹，所以只能当兜底，不能当主力。如果最终选了同步工具，那 Chrome 那边留着也只是多一份冗余副本，不会自动互相干扰——两边是各自独立的同步通道。

### Chrome 的登录账号书签会一起同步到 Firefox 吗？

会，但它们在 Firefox 端的落点是本地「其他书签」下的同名文件夹，而不是像 Chrome 那样有一个独立账号根。Firefox 没有账号子树概念。BookmarkSync 明确选择退到本地「其他书签」，而不是退到 Chrome 的账号子树——后者是 Chrome 自动同步管理的，扩展往里写等于把书签上传到用户的 Google 账号，位置对了归属就错了。

### Firefox 那个 `tags________` 文件夹为什么同步工具要跳过？

它是 Firefox 内部用来管理书签标签的文件夹，不是用户书签。捕获它会生成一批幽灵节点，而且删不掉——Firefox 会重建。这类属于浏览器内部结构的文件夹，同步时不该碰。

### 迁过去之后 Firefox 的 Sync 要不要开？

看你是不是要多设备用。如果只是 Chrome 一台机器 + Firefox 一台机器，靠 BookmarkSync 这类跨浏览器通道就够了，Firefox Sync 反而会引入合并冲突——它会把两边当同一份数据合并，而你已经有一份跨浏览器同步在跑了。同时开两套同步引擎处理同一批书签，冲突是迟早的事。如果你要在多台设备之间用 Firefox，那开 Firefox Sync、但把跨浏览器同步留给另一部分书签，是更清楚的做法。
