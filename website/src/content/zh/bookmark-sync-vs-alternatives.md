# 书签同步工具怎么选：五款工具按事实对比

选书签工具时最容易踩的坑，是把两类完全不同的东西放在一起比：一类是**同步引擎**（把你浏览器里的书签搬运到别的浏览器，书签仍然待在你的书签栏里），另一类是**书签管理器**（把书签收进它自己的面板，浏览器书签栏是空的）。它们都能叫「书签工具」，但解决的不是同一个问题。

这篇把五款常见工具按可核实的事实摆在一张表里，然后逐条说差异在哪、什么情况下该选别人。

## 先分清两类工具

**同步引擎**：Floccus、XBrowserSync、BookmarkSync。它们读写浏览器自己的书签树，装完之后你打开书签栏看到的还是那些文件夹和链接，只是别的浏览器里也有了。它们的价值在「搬运」和「保持一致」。

**书签管理器**：Raindrop.io、Cubox。它们的价值在「组织」——集合、标签、全文搜索、稍后阅读。书签存在它们自己的界面里，浏览器书签栏不会因此多出东西。你需要找链接时，得记得去打开那个面板。

这两类不是竞品关系。如果你想要的是标签和全文搜索来管理几千条资料，管理器更合适；如果你想让 Chrome 里存的书签出现在 Edge 和 Firefox 的书签栏里，管理器帮不上忙——它只是把你的书签从 iCloud 搬到了另一个应用。

## 对比矩阵：先看同步引擎

三款同步引擎放在一起比才有意义——它们做的是同一件事。

| 对比项 | BookmarkSync | Floccus | XBrowserSync |
|---|---|---|---|
| 同步到原生书签栏 | ✓ | ✓ | ✓ |
| 无需自建服务器 | ✓ | ✗ 需 WebDAV / Nextcloud | ✗ 需自建同步服务 |
| 端到端加密 | ✓ 默认开启 | 需手动设口令 | ✓ 默认开启 |
| 真树结构，改名/移动不丢子项 | ✓ | ✓ | ✓ |
| 删除精准传播、不会复活 | ✓ | ✓ | ✓ |
| 多端并发合并、互不覆盖 | ✓ | △ master 侧优先 | ✗ 整树覆盖 |
| 冲突全自动收敛，无需人工处理 | ✓ | △ 保险丝可中止同步 | ✗ 改动被覆盖，需重做 |
| 书签顺序跨设备保持 | ✓ | ✗ 已知问题 | ✓ |
| 多空间隔离（工作 / 生活） | ✓ | ✗ | ✗ |
| 免费档 | 1,000 条永久免费 | 免费，但服务器自付 | 免费，需自建服务器 |

## 再和书签管理器划清界限

Raindrop.io 和 Cubox 不搬书签，所以「改名丢不丢子项」「合并会不会覆盖」这类问题对它们不适用——它们压根不碰你浏览器里的树。真正该比的只有一件事：书签到底存在哪。

| 对比项 | BookmarkSync | Raindrop.io | Cubox |
|---|---|---|---|
| 同步到原生书签栏 | ✓ | ✗ 自有面板 | ✗ 自有面板 |
| Chrome ↔ Edge ↔ Firefox | ✓ | 经面板中转 | 经面板中转 |
| 无需自建服务器 | ✓ | ✓ | ✓ |
| 端到端加密 | ✓ 默认开启 | ✗ 非 E2EE | ✗ 非 E2EE |
| 标签 / 全文搜索 / 稍后阅读 | ✗ | ✓ | ✓ |
| 免费档 | 1,000 条永久免费 | 免费增值 | 付费 |

两张表里最容易被误读的两点，先说清楚。

**「不适用」不是「不支持」。** 一个不搬书签的管理器，谈不上「改名丢不丢子项」——它压根不碰你浏览器里的树。所以管理器的那些维度直接不出现在第二张表里，而不是打叉。

**「需手动设口令」和「默认开启」是两件事。** Floccus 的 E2EE 是按存储后端给的：Nextcloud Bookmarks、WebDAV、Google Drive、Dropbox 支持加密，Git 后端不支持。而且它要你在配置账号时自己设一个口令，所有设备都得用同一个——不设就是明文。BookmarkSync 和 XBrowserSync 是默认就加密，用户不需要知道「加密」这个选项存在。

## Floccus：最灵活，代价是你要有台服务器

Floccus 是这几款里最成熟的纯同步引擎，开源、跨浏览器、确实写原生书签栏，真树同步和合并语义也做得对。如果你的技术背景够，它几乎没有硬伤。

它的门槛全在部署上：同步需要一个后端，可以是 Nextcloud Bookmarks 应用、一个 WebDAV 空间、Google Drive、Dropbox，或者一份放在 Git 里的文件。对开发者来说这是十分钟的事，但「推荐给不懂技术的家人」就行不通——他们要先去注册一个 Nextcloud 或者买个 WebDAV 服务。

书签顺序是它已知的短板。Floccus 没有排序设置，顺序由「后端怎么存」和「两个客户端合并时怎么交错」共同决定，多设备合并之后顺序可能和你手动拖出来的样子不一致。官方 issue 里这个问题长期挂着，实用解法是「认定一台设备为准、其他设备只读」，或者干脆接受顺序会被重排。

## XBrowserSync：开源、默认加密，但整树覆盖

XBrowserSync 的思路很干净：装扩展、连一个同步服务器、书签保持一致，全流程默认端到端加密，服务器只存密文。

它的问题在并发语义上。每次同步是**整棵书签树**作为一个密文快照上传，服务端只比较 `lastUpdated` 和版本号，谁的时间戳新就保留谁——不是逐条合并。两台设备同时改，后上传的那份会把前一份的改动整体覆盖掉。它会在覆盖前提示「服务器上有更新的版本」，但提示本身救不了已经在两边各改了一半的情况。

另一个现实问题是维护节奏。它的服务端 API 长期停在同一个版本线上，依赖树偏旧；公共同步服务器能不能长期可靠，一直是用户讨论的点。自建可以解决可靠性，但那就回到「你得自己维护一台服务器」的老问题上。

## 为什么他们的冲突要人管，我们的不用

这一节是全文最技术、也最能说明差别的地方。先把一个常见误解澄清掉：**这几款工具都不会弹窗问你「保留 A 还是保留 B」**。它们的冲突处理是自动的——问题在于「自动」之后你要做的事。

### XBrowserSync：改动被覆盖，工具请你「重做一遍」

它的同步单位是整棵树的密文快照。服务端只比较时间戳和版本号，谁新留谁。两台设备各改了一半，后上传的那份把前一份整体覆盖。

它的界面文案把这件事写得很直白（`res/strings/en.json`）：

> `Sync conflict detected` — "Local data was out of sync and has now been refreshed. **Please reapply last change.**"

翻译过来就是：**你刚才那次修改被冲掉了，麻烦重新做一遍。** 这不是让你选择，是让你重做。

### Floccus：不覆盖，但会中止同步或留下重复项

Floccus 用三方合并（cache 快照 + 本地树 + 远端树），比整树覆盖精细得多。但它的「自动」在几种情况下会把活儿推回给人：

**一、保险丝直接中止同步。** 它有一个防误删阈值，一旦这次同步要删掉的条目超过比例，就整个不执行（`strategies/Default.ts` 的 `applyDeletionFailsafe`）：

> `E029: The current sync run would delete {0}% of your links on the server. **Refusing to execute.** Disable this failsafe in the profile settings if you want to proceed anyway`

同步不跑了，你得自己去设置里关掉保险丝。这算不算「人工介入」？算，而且是在你最不确定数据对不对的时候，要求你做一个更不确定的决定。

**二、并发修改按「master 侧优先」裁决。** 源码里 `masterLocation` 固定指向本地（`Default.ts:625`），并发 UPDATE 和 MOVE 的裁决是「master 优先，另一侧不做」（`Default.ts:1488`、`:1320`）。它不报错、不提示，远端那次修改就没了。同一组改动在不同设备上可能得到不同结果——因为「master」是相对每台设备而言的。

**三、没有 cache 时不传播删除。** 首次同步、清过缓存、换了设备之后走的是 `Merge` 策略，源码注释写得很明确（`Merge.ts:60`）：`a copy of DefaultSyncProcess#reconcileDiffs without anything involving REMOVEs`。它只合并新增和修改，**删除不同步**。重复项靠「书签比 URL、文件夹比标题」这种启发式去重，去不掉的要人手工清。

### BookmarkSync：结构层面不存在「冲突」这个状态

我们用 Move-CRDT（Kleppmann 等人 2021 年的可复制树移动操作）。核心在 `src/crdt/moveCrdt.ts` 的 `apply_op`，它实现的是论文 Fig.4 的收敛语义：

> the state of the tree is **as if all operations had been applied using do_op in increasing timestamp order, regardless of the order in which they were actually applied**

换成人话：不管各设备的操作以什么顺序到达，最终结果只由「操作集合」决定，不由「到达顺序」决定。所以：

- **删除**是「移动到回收站节点」（`TRASH_NODE_ID`），不是覆盖或比对——A 删掉的书签不会因为 B 还有旧数据而复活；
- **移动**用 Lamport 时间戳定序，会成环的操作被拒绝但仍记入日志，保证各副本 undo/redo 一致；
- **不需要 cache 快照**，也就不存在「cache 丢了就退化成不传删除」这种情况；
- **没有保险丝**——因为不存在「这次同步会不会误删」的判断，删除本身就是一次确定的移动。

结果是：**没有「请重做一遍」，没有「拒绝执行」，没有「关掉保险丝再试」，也没有需要你手工清理的重复项。**

### 一个必须说清的边界

CRDT 收敛的是**结构**（谁在谁的下面、存在与否），不是**字段**。

同一个书签的标题被两台设备同时改名，仍然是**后写者赢**（`types.ts` 里写明了 metadata 是 `LWW by timestamp`）。这一次改名会被静默丢弃。

区别在于：这是**确定性的、不需要你做任何事**的结果，而不是「同步停了等你处理」或「你的改动没了，请重做」。我们不会假装这里没有取舍——只是这个取舍不会把人卷进来。

| | 冲突表现 | 要人做什么 |
|---|---|---|
| XBrowserSync | 整树覆盖 | 重做被覆盖的改动 |
| Floccus | 中止同步 / master 侧静默丢弃 / 重复项 | 关保险丝、接受丢失、手工清理 |
| BookmarkSync | 结构自动收敛；同字段并发改名后写者赢 | 无 |

## Raindrop.io 与 Cubox：管理器，不是同步工具

这两款产品本身做得很好，Raindrop 的集合、标签、全文搜索是这类工具里的标杆，Cubox 在国内的稍后阅读体验也成熟。它们的定位是**收藏与研究管理**，不是「让 Chrome 的书签出现在 Edge 里」。

判断标准很简单：如果你会为了找一个链接而专门打开一个面板，那它们合适；如果你希望链接就待在你本来就会看的书签栏里，那它们解决不了——它们只是把「书签在别的地方」这件事，从 iCloud 换成了另一个应用。

## BookmarkSync 的差异在哪

我们做的事和 Floccus、XBrowserSync 是同一类：写浏览器原生书签树。差别在几件具体的事上。

**不用自建服务器。** 注册即用，同步服务由我们托管。这是把 Floccus 的部署门槛整个拿掉。

**端到端加密默认开。** 每一条书签操作都在你的设备上加密后才上传，服务器只保管密文。密钥不落服务器，新设备用同一口令即可解密。

**真树结构，不是路径字符串。** 有些同步实现把书签存成 `书签栏/工作/子项` 这样的路径字符串，父路径一改，子项就找不到家——这是「文件夹改名后子项全没了」的根因。我们按节点同步，改名、移动、重排之后子项和层级完整保留。

**删除是一次确定的移动，不是比对。** 删除被建模成「移到回收站节点」这个操作，A 设备删掉的书签，不会因为 B 设备上还有旧数据而复活。

**并发改动由 CRDT 收敛，不是三方合并。** 两台设备同时增删改，各自的新增都保留；离线改的，联网后照样并起来——结果只由操作集合决定，与到达顺序无关（详见上一节）。

**顺序会跟着走。** 拖拽重排之后，其他设备保持同样的顺序。引擎按排序键收敛，不会把排列打乱成内部编号序。

**多空间隔离。** 工作一套树、生活一套树，各自绑定不同的浏览器资料，切换空间即切换同步上下文。这一条在上面四款里都没有。

## 什么情况下该选别人

诚实地说，有三种情况我们不是最优解。

**你要的是研究资料管理，不是同步。** 想要标签、全文搜索、跨设备稍后阅读——Raindrop.io 比我们成熟得多，它在这个方向上做了很多年。

**你已经有 Nextcloud，并且希望数据完全在自己手里。** Floccus 直接对接你现有的 WebDAV 或 Nextcloud，不需要信任任何第三方服务。我们做不到「服务端完全由你控制」，这是托管服务的固有代价。

**你需要 Safari 同步。** 这一条要说清楚：Safari 的扩展模型不支持 `bookmarks` API，任何工具想同步 Safari 原生书签栏，都必须有一个原生 macOS 组件来当桥。我们目前只做 Chrome / Edge / Firefox，没有 Safari 支持，也不打算靠一个半成品应用来凑。如果你的核心诉求是 Safari 与 Chrome 互通，现阶段更适合去看有 macOS 配套应用的方案。

## FAQ

### 这些工具能同时装吗，会不会互相打架

不建议在同一个浏览器上同时启用两个会写书签的同步工具。它们各自维护一份「应该是什么样」的认知，同时写入同一棵树时会互相判成对方的改动是脏数据，结果通常是反复来回覆盖。换工具之前先停用旧的，并手动导出一份书签备份。

### 两台设备同时改，需要我手动选保留哪边吗

不需要。结构层面（书签存在与否、挂在哪个文件夹下、顺序）由 CRDT 自动收敛，结果只由操作集合决定，与到达顺序无关，不会出现「同步停了等你处理」。

唯一的例外是同一个书签的标题或网址被两台设备同时修改——这时按时间戳后写者赢，先写的那次静默丢弃。这是确定性的结果，不需要你做任何操作，但也确实不是「两次修改都保留」。

### 「端到端加密」怎么验证，不是听厂商说

几个可验证的判据：密码重置是否需要服务器参与（真 E2EE 下服务器没有你的密钥，重置只能清空重来）、网页预览是否需要你输入口令、是否公布了算法名与 KDF 迭代次数、服务端能否读出一条书签的标题。更完整的检查清单可以看站内那篇专门讲验证方法的文章。

### 免费档够用吗

我们的免费档是 1,000 条书签、1 个空间、最多 3 台设备，永久免费，同步能力与付费档完全一致——三档只在书签数量、空间数和设备数上有差别。大多数人的书签量在几百条量级，免费档就够。

### 换工具时怎么保证不丢书签

先导出一份 HTML 备份。它只花一分钟，却是唯一能让你撤销一次糟糕同步的东西。然后停用旧工具、确认浏览器里的书签树是你要的样子，再装新工具做首次同步。首次同步之后逐层核对文件夹数量，别只看总数。

### 为什么不做 Safari

Safari 从 2011 年起就不提供 `bookmarks` API，至今没有恢复。这不是实现难度问题，是平台没给接口——唯一可靠的路径是写一个原生 macOS 应用直接读写 Safari 的书签库，还要处理它和 iCloud 的同步关系。这件事我们评估过，结论是当前阶段不做半成品：与其提供一个会丢数据的 Safari 同步，不如明确说暂不支持。
