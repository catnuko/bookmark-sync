# 怎么判断一个书签同步扩展是真端到端加密：一份检查清单

几乎每个书签同步扩展的页面都会写「端到端加密」。这句话的信息量接近零——因为纯文本存储也能在页面上写这四个字。真正有区别的地方在流程细节里，而其中大部分可以自己验证。这份清单按「能不能自己动手测」排序，前五条不需要任何技术背景。

## 最关键的一条：他们能不能给你发「重置主密码」的邮件

把这条单独拎出来，因为它比其他所有判据都强。

假设一家服务商**能**给你发一封「重置你的主密码」的邮件链接，这封邮件的存在本身就证明了至少一件事：**他们手上有你的密钥，或者他们有办法验证你的密钥。**

这两件事和端到端加密是互斥的。真 E2EE 的前提是服务端只有密文、没有密钥。能验证你的密钥意味着服务端持有一个能跟你的密文对上的东西——那这个东西就是密钥，或者等价物。

所以：

| 你能做的事 | 它证明了什么 |
|---|---|
| 忘记密码，客服帮你重置 | 服务端有密钥或可验证密钥 → 不是真 E2EE |
| 收到「重置主密码」的邮件链接 | 同上，链接本身就是证据 |
| 忘记密码，只能自己重设且历史数据丢失 | 真 E2EE 的典型表现 |
| 换设备时只需口令，不需要别的 | 服务端托管了盐值等参数，但没有密钥 |

最后一行是一个需要区分的细节。**「换设备不用记 44 位密钥」本身不能证明是假 E2EE。** 真 E2EE 的困难恰恰在于密钥必须由用户保管，而把盐值、迭代参数这类非秘密参数托管在服务端，是为了免去用户手动抄写密钥的负担——这不泄露密钥。

我们就是这么做的：换设备只需同一口令，关键参数（盐值）服务端托管，但主密钥永远由用户口令派生，服务端不保存。

### 直接的验证动作

在注册第二个账号或者用另一台设备时，故意**不保存口令，看你还能不能回来**。

- 回来得了，且历史书签完整 → 服务端有密钥或等价物
- 回不来，历史数据不可恢复 → 真 E2EE

再具体一点：注册后立刻导出一份书签，然后把账号密码清空，只留浏览器里的会话。之后退出登录，看能不能在不知道任何密钥的情况下恢复访问。恢复成功就说明服务端能替你解开数据。

## 判据二：网页预览要不要密码

很多服务提供一个「在浏览器里预览你的书签」的页面。这个页面需要密码吗？

- 不需要密码，点开就能看到你的文件夹名和网址 → 服务端能解密 → 不是真 E2EE
- 需要密码，或者根本没有网页预览功能 → 符合真 E2EE 的形态

这个判据容易被绕过：厂商可以说「预览功能我们做了端到端加密，在浏览器里解密」。这句话技术上可能成立，但它引出下一个问题——

**预览页面的代码本身是服务端下发的。** 如果解密密钥被送到浏览器里完成解密，那么服务端控制着那段代码。你可以认为能改这段代码的一方，也就是服务商自己，有能力在代码里加入任意逻辑，包括把你的明文发出去。

所以判据二要问的不是「预览功能有没有密码」，而是**「有没有网页预览」**。一个真 E2EE 的产品通常压根不做服务端渲染的预览，因为这个位置天然不可信。

## 判据三：有没有公布算法名

不公布算法名是个明确的负面信号。

加密不是玄学。成熟方案就那么几种：AES-256-GCM、ChaCha20-Poly1305、XChaCha20-Poly1305。密钥派生通常是 PBKDF2 或 Argon2。公布算法名不会让攻击变容易——攻击者本来就知道你会用什么，真正的安全性在密钥长度和实现质量上。

不公布只有两种可能：还在换，或者不想让你验证。两种都不好。

我们用 AES-GCM。顺带说，128 位的密钥在密码学上已经不构成任何有效防护，这个数字现在是营销话术而不是技术参数。

## 判据四：密钥派生的迭代次数是多少

这是最容易被忽略、也最能看出认真程度的一项。

客户端加密的安全性有一大半不在加密算法本身，而在**从一个弱口令（你脑子里那个）推导出强密钥的过程**。人用的密码就那么几十位熵，暴力枚举完全可行。密钥派生函数的作用就是把这个成本放大到不可接受——迭代次数就是放大倍数。

对 PBKDF2-SHA256 来说：

| 迭代次数 | 含义 |
|---|---|
| 1,000 次 | 2000 年代初的默认值，现在等于没有防护 |
| 10,000 次 | 明显低于当前建议 |
| 100,000 次以上 | 合理的范围 |
| 600,000 次以上（OWASP 2023 建议配SHA-256） | 达到当前推荐档 |

Argon2 系列的参数不能直接换算成 PBKDF2 的迭代次数，但判断方式一样：**看有没有给**。给了说明经过了思考，没给说明密钥派生这一步大概是随手写的。

一个补充判断：如果服务商把 KDF 参数存在服务端（我们存盐值就是出于这个考虑），那这些参数必须**在每个设备上保持一致**，否则同一口令会派生出不同密钥。这是个隐含的一致性要求，实现难度比看上去高。

## 判据五：有没有第三方审计

自己说「我们是真 E2EE」没有说服力。第三方审计的意义在于审计方能看到你不想让人看到的东西——服务端代码、密钥处理流程。

审计报告要看的不是「通过了」，而是**范围**：

| 审计范围 | 说明 |
|---|---|
| 只审客户端 | 服务端仍不可信，价值有限 |
| 只审加密函数本身 | 太窄，不涉及整体设计 |
| 服务端 + 客户端全链路，含密钥生命周期 | 这才是有意义的范围 |
| 定期复审 | 密码学实现会变，一次审计不够 |

还要看是谁审的、有没有公开报告。报告不公开的话，审计的存在意义打对折。

## 判据六：是不是开源

开源不保证安全（有多少行代码带后门的开源项目），但它保证**可验证性**——你不必信任作者，你可以自己看。

对 E2EE 尤其如此，因为 E2EE 的全部价值就是「你不信任服务端」。一个不公开实现的服务端加密，本质上是要求你信任它，而它恰恰是你声明不信任的对象。

这条要留个例外：**开源不等于服务端开源。** 有些产品只开源客户端和协议，服务端闭源。这种情况下你能验证的是「客户端不偷数据」，不是「服务端没被改」。真做到位的话，客户端加密部分和服务端数据格式都应该公开。

## 判据七：服务端存的东西长什么样

这一条需要打开开发者工具，但只需要十秒。

在浏览器里登录服务商，看它的网络请求和返回的数据结构。真 E2EE 的服务端存的东西应该接近这个形状：

```
{ iv, ciphertext }
```

只有 IV 和密文。没有明文字段，没有文件名，没有大小统计。

如果返回里能看到文件夹名、URL、书签标题、或者一个 `folders` 数组带可读名称——那不管它管这叫「端到端加密」还是别的什么，数据在服务端是可读的。

再补一个更严格的检查：**看有没有 `size`、`count` 这类元数据。** 服务端如果报告「你有 342 条书签」，那它在数你的数据。真 E2EE 下服务端只能知道字节数。

我们用 `space_id` 作为 AAD（附加认证数据）。AAD 不加密但被纳入完整性校验，作用是把密文绑定到具体空间：A 空间的密文拿到 B 空间用会直接校验失败。这个字段在传输时会出现在结构里，但它是一个 ID，不是内容——这跟「服务端能看到明文」是两回事，别混淆。

## 对照表：七条判据

| 判据 | 真 E2EE 的表现 | 假 E2EE 的表现 |
|---|---|---|
| 密码重置 | 只能重设，历史数据不可恢复 | 客服或邮件链接可重置 |
| 网页预览 | 没有服务端渲染的预览 | 点开就能看，或要求密码 |
| 算法名 | 明确公布 | 含糊或不提 |
| KDF 迭代 | 给出参数和依据 | 不提，或明显偏低 |
| 第三方审计 | 全链路含密钥生命周期 | 只审局部，或报告不公开 |
| 开源 | 客户端与服务端数据格式都公开 | 只有宣传页 |
| 服务端数据 | 只有 IV、密文和不可解读的元数据 | 有明文标题、URL、文件名 |

## 拿 Chrome 原生同步对照一下

Chrome 原生同步是一个有用的参照，因为它的设计目标是**便利**，不是隐私。

关键事实：**Chrome 默认不开端到端加密。** 书签和历史以明文存在 Google 的云里，除非你手动设置一个同步口令（sync passphrase）。手动设置之后，数据会加密，而 Google 不参与解密过程。

设置之后还有两个必须知道的例外：

1. **支付方式不受同步口令保护。** 你在 Chrome 里保存的信用卡信息不在这个加密范围内。
2. **地址也不受保护。** 你的地址簿以明文形式存储和同步。

这不意味着 Chrome 有问题——它把密钥存在你的 Google 账号上，Google 理论上能拿到密钥，密码学上确实不是 E2EE。但它在密码学之外的层面做得更好：数据在磁盘上、在传输中、在 Google 的存储里都是加密的（Google 声称静态加密），这些用的是标准的服务端加密密钥管理。

**这是两种不同的信任模型。** Chrome 要求你信任 Google 的密钥管理；真 E2EE 要求你不信任任何人。

对比的结果不是「Chrome 差、真 E2EE 好」。Chrome 在密码学之外做了很多事，而纯 E2EE 产品经常在易用性上落后很多。判断的依据是你要防什么威胁：

| 你想防的 | 对应的合理选择 |
|---|---|
| 服务商员工偷看、或者被入侵时数据泄露 | E2EE |
| 公司 IT 管理员看到你的浏览器数据 | E2EE |
| 传输途中被截获 | 原生同步也够（TLS + 静态加密） |
| 服务商因法律要求交出你的数据 | E2EE |
| 想要最少的功能、最少的账号 | 原生同步 |

如果你只是在同步几千条书签，不涉及敏感内容，原生同步的可用性优势是实在的。这篇不是在说 E2EE 是唯一正确选择，是在说「E2EE」这个词本身不携带信息，你需要用上面七条去换掉那个宣称。

## FAQ

### 服务商支持「忘记密码重置」，是不是就说明不是端到端加密？

基本是。这条是判据里最强的。

能重置密码意味着服务端持有一个能解开你数据的密钥，或者至少有一个能验证你密钥的东西。这与真 E2EE 直接冲突——真 E2EE 的前提就是服务端只有密文。

反过来，「忘记密码只能重设、历史数据丢失」不是设计缺陷，是端到端加密的必然结果。

### 网页预览需要密码，还算端到端加密吗？

要分情况。

如果预览是在浏览器本地完成的（你输入口令，扩展在你的机器上解密，页面从不经过服务端），那可以算 E2EE。

如果解密发生在服务端渲染的页面上，无论加不加密码都要打问号——因为那段代码是服务端下发的，服务商有能力改它。真正的判断标准是「有没有服务端渲染的预览」，而不是「预览要不要密码」。

### 不公布加密算法，会不会是安全的表现？

不会。

加密算法公开是正常做法。攻击者本来就知道你会用什么，真正的安全性来自密钥长度、实现质量和密钥派生强度。公布算法名不降低任何安全性。

不公布只有两种解释：还没选定，或者不希望你验证。两种都不值得信任。

### 用迭代次数很高的 KDF，会不会让同步变慢？

会一点，但通常感知不到。关键是 KDF 只在**派生密钥**时运行，不是每次同步都跑。密钥派生一次之后就放在内存里用了，所以高迭代次数影响的是登录或解锁的耗时（可能几秒），不是每次同步的耗时。

反过来，如果你发现每次同步都很慢，那可能说明实现有问题——比如每次同步都重新派生了一遍密钥。

至于加密本身的开销，可以忽略：AES 在现代硬件上有硬件加速，几百条书签的加密是毫秒级。真正影响同步速度的是上传带宽和并发处理能力，跟加不加密没有因果关系。如果某个服务明明白白告诉你「因为要加密所以慢」，这个说法通常是找借口。

### 我们应该自己审查一个工具吗？

审查全部代码不现实，但可以做局部验证，而且价值不低：

- 打开开发者工具看服务端返回的数据结构（十秒钟，判据七）
- 测试忘记密码后的恢复流程（判据一）
- 看它是开源的、审计报告在不在（判据五和六）

这三条加起来不到半小时，能挡掉大部分虚假的宣称。剩下的深入审查交给第三方审计机构，你至少要确认审计存在且范围覆盖了服务端。

### 我们的 E2EE 和别家的有什么区别？

技术基础相同：都是客户端加密，服务端只见密文。

几个具体选择：算法用 AES-GCM，AAD 绑 `space_id` 让密文无法跨空间复用；关键参数（盐值）服务端托管，换设备只需口令而不用记 44 位密钥；配额按字节算而不是条数——这不是偷懒，而是 E2EE 下服务端唯一能强制执行的计量指标就是字节数，单条书签密文约 2 KB，所以 Free 档 1,000 条对应 5 MB（按 2 KB/条 算约 2 MB，留了余量）。

顺带一提，Auto 整理功能只调移动和创建接口、从不调用删除，这条限制来自两次删数据事故的教训，跟加密无关。
