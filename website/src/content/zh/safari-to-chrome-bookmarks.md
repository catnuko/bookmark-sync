# Safari 书签迁移到 Chrome：会丢什么，最快的路径是哪条

Safari 的书签搬到 Chrome，最快的方式既不是导文件也不是装工具，而是 Apple 自己提供的 iCloud Bookmarks 扩展——装上之后 Chrome 直接读 iCloud 里的书签，几分钟完事。但它只读，而且 Safari 有几个东西在 Chrome 里根本没有对应概念。这篇先说清会丢什么，再说怎么做。

## 迁移前要知道什么

### Safari 的书签存在哪，以及为什么它不能直接被读取

Safari 的书签**不在** `~/Library/Safari/Bookmarks.plist` 这个位置上被浏览器以常规方式使用。这个 plist 是二进制的 Apple 专有plist 格式，而且现代 macOS 上 Safari 实际读取的是 iCloud 里的书签数据，本地 plist 更像是缓存或兼容产物。

这意味着两件事：任何第三方工具想直接读 Safari 书签，都要先处理这个二进制 plist；而更根本的是，**通过文件读不是 Apple 打算让你用的路径**。Apple 给的路径在下一条。

### 首选路径是 Apple 官方的 iCloud Bookmarks 扩展

这是最该先试的方法，因为它同时满足快、安全、不需要第三方接触你的数据三个条件。Apple 官方的 iCloud Bookmarks Chrome 扩展装上之后，Chrome 可以直接读取你 iCloud 里的书签，**不需要导出、不需要中间文件、不需要任何转换**。

对比一下其他方式要经过多少环节：

| | iCloud Bookmarks 扩展 | 手动导出 HTML 再导入 | 第三方迁移工具 |
|---|---|---|---|
| 谁接触你的数据 | 只有 Apple 和 Google | 只有你自己 | 取决于工具 |
| 速度 | 装完就看到 | 十几分钟 | 几分钟 |
| 需要 Apple ID | 是 | 否 | 否 |
| 能否只读 | **只能读** | 不适用 | 双向 |
| 空中间层文件夹 | 保留 | **会丢** | 保留 |
| 书签顺序 | 保留 | **会重排** | 保留 |

> 但要说清楚：这个扩展**只读**。它在 Chrome 侧不会把改动写回 Safari，你也不能靠它做持续同步。它解决的是「一次性把书签拿过来」，不是「两边长期保持一致」。

而且它依赖 Apple ID 登录状态。如果你不想让 Google 侧接触到你的 iCloud 内容，或者你压根没在用 iCloud 书签，这条路走不通——那就看下面的原生导入和验证步骤。

### 阅读列表和智能文件夹在 Chrome 里没有对应概念

这是 Safari 书签迁移里真正会丢的东西，也是最少被提及的。

Safari 有两个 Chrome 完全没有的概念：

- **阅读列表**（Reader）：Safari 独立维护的一个「稍后读」列表，它和书签是两个东西，但很多人混在一起用。Chrome 里没有阅读列表这个功能，对应物是「稍后阅读」或第三方扩展，两者行为不完全一致。
- **智能文件夹**：基于规则动态聚合的文件夹，比如「含未读」「最近添加」「有特定标签的」。它是查询而非实体——里面的条目由规则算出来，不是一份静态清单。

迁移的时候你会发现它们**没有被迁过去**，因为格式里没有位置放它们。HTML 书签格式只认识「文件夹」和「书签」两种东西，没有任何字段能表达「这是动态聚合的」或「这是阅读队列」。

> 处理办法：迁移前先在 Safari 里把阅读列表里真正想留的文章，手动存成普通书签（Cmd+D）。智能文件夹里如果有一批你想保留的，展开后全选另存为普通文件夹。手动麻烦一次，但不会漏。

### 书签顺序不会导出——这是格式限制不是 bug

这条值得单独说，因为很多人以为是工具没做好。HTML 书签格式（也就是 Netscape Bookmark File Format）**没有顺序字段**。文件夹里的条目在文件里可以按字母排序存储，但「你在 Safari 里手动拖成的样子」这个信息在导出时不存在。

所以迁到 Chrome 后你会发现顺序变了——通常变成字母序或导入时间序。**这不是 bug，是格式本身承载不了这个信息。** 任何走 HTML 的迁移都必然重排顺序。

如果你很在意顺序，办法是记在脑子里或记在笔记里，迁完手动拖一次。一次性成本。

### Chrome 侧的代价：什么不受同步口令加密

这条和安全直接相关，Google 官方文档里写明了。Chrome 的同步加密范围是有限的：**支付方式和地址不受同步口令（sync passphrase）加密。**

也就是说，如果你给 Chrome 同步设了口令，别以为「所有东西都被加密了」。书签在它的保护范围内，但支付方式、地址这些字段不在。

这一条对迁移决策的影响是：如果你对「Google 拿到多少数据」敏感，那么从 iCloud 走官方扩展（书签经过 Apple 和 Google 两家）比走文件导入再由你手动上传要多一层数据流转。纯本地导入（导出 HTML 后你在 Chrome 里自己导入）数据不经过额外的第三方，是流转最少的方式。

## 两条迁移路径

除了上面的 iCloud 扩展，实际可选的是这两条：

| 对比项 | 原生导入（Safari 导出 → Chrome 导入） | 跨浏览器同步工具 |
|---|---|---|
| 速度 | 一次性，十几分钟 | 装好后长期生效 |
| 空中间层文件夹 | **会丢** | 保留 |
| 书签顺序 | **会重排** | 保留（每条带排序键） |
| 之后两边来回改 | 完全做不到 | 可以 |
| 数据经过谁 | 只有你自己 | 工具的服务器（默认 AES-GCM 加密，服务端只存密文） |
| Safari 侧支持 | 不需要 | **目前不支持 Safari 扩展** |

**关键区分：原生导入是「一次性搬家」，同步工具是「跨浏览器持续同步」。** 但对 Safari 这条路要说实话：BookmarkSync 目前**不支持 Safari**，没有 Safari 扩展。所以如果你要的是「以后 Safari 和 Chrome 长期双向同步」，现在还做不到，别指望。

现阶段务实的组合是：**用原生导入完成一次性搬家，之后靠 Chrome 侧的同步在多台设备间保持一致**。真要保留「Safari 也参与」的能力，靠 iCloud 书签和 iCloud 标签（Tags）在 Apple 生态内部保持 Safari 自己的那一套。

## 动手步骤

### 路径一：用 Apple 官方 iCloud 扩展（推荐先试）

1. 确认你的 Safari 书签已经同步到 iCloud。打开 iCloud 设置，确认「书签」这一项是打开的；打开 Mac 的「系统设置」→ Apple 账户 → iCloud，能看到书签的开关。
2. 在 macOS 上安装 Apple 官方的 iCloud Bookmarks Chrome 扩展。这一步需要你登录自己的 Apple ID，Apple 不会把它交给任何第三方。
3. 装好后在 Chrome 里打开书签管理器，扩展会在侧栏里提供 iCloud 书签的入口。首次加载可能要等一会儿，取决于你的书签数量和 iCloud 状况。
4. 逐个点开你的顶层文件夹，确认层级和条数和你预期一致。注意这个扩展是只读的，你在 Chrome 里做的任何改动都不会写回 Safari。
5. 确认无误后，去 Chrome 设置 → 同步，打开「书签」开关，让这些书签进入 Chrome 自己的同步体系（注意上面说的：支付方式和地址不受同步口令加密）。

### 路径二：手动导出再导入（不依赖 iCloud）

1. 在 Safari 里先处理会丢的东西：把阅读列表里想留的文章手动存成普通书签，把智能文件夹展开另存为普通文件夹。这步别偷，跳过了就是永久丢失。
2. 选中要迁移的文件夹（或者按 Cmd+A 全选），在右键菜单或文件菜单里选「导出为书签」。也可以在「个人收藏」这个书签文件夹上右键，选「导出为书签」，导出的 `.webarchive` 里会带上文件夹结构。
3. **打开导出的文件看一眼。** 如果你记得有「中间层没有直接书签」的文件夹，搜一下——搜不到就说明这层已经丢了。
4. 打开 Chrome，进书签管理器（`chrome://bookmarks`），右上角三点菜单 →「导入书签和设置」。
5. 选择「HTML 文件」这一项，指向第 2 步导出的文件。导入位置选「导入的书签文件夹」，这样不会打乱你现有的书签。
6. 导入后按下面「怎么验证」对一遍，再去清理那些多出来的空目录。

## 怎么验证迁移成功

1. **对总数。** 先在 Safari 侧数一遍书签条数（不含文件夹），再在 Chrome 侧数一遍。对不上，先确认是不是把文件夹算进去了，或者某条书签是重复的。
2. **验层级。** 挑一个你印象很深的嵌套文件夹，逐层点开。数量对但层级被拍平，是 HTML 迁移最典型的失败形态。
3. **确认阅读列表和智能文件夹的处理是你要的。** 迁移前没手动转的话，这部分就是丢了。回去在 Safari 里把要留的补成普通书签，再导一次增量。
4. **看顺序。** 顺序变了是格式限制，不是迁移失败。但如果你对某个文件夹的顺序有要求，现在手动拖一次，因为再导一次还会乱。
5. **清掉多出来的空目录。** HTML 格式丢中间层时会留下这类残留。它们没有用，删掉即可——但删掉的同时你要知道这次迁移确实丢了信息。

## FAQ

### Safari 书签能不能直接导入 Chrome，不用导出文件？

可以，而且这是首选方式。Apple 官方的 iCloud Bookmarks Chrome 扩展让 Chrome 直接读 iCloud 里的书签，不需要导出文件和中间转换。前提是你的 Safari 书签已经同步到 iCloud，并且你愿意在 Chrome 侧登录状态下让这条链路存在。局限是这个扩展只读，Chrome 侧的改动不会写回 Safari。

### 迁移之后书签顺序全变了，是迁移失败了吗？

不是，这是格式限制。HTML 书签格式没有顺序字段，你在 Safari 里手动拖出来的排列次序在导出时不存在。导入后通常变成字母序或导入时间序。任何走 HTML 的迁移都必然重排顺序。真要恢复，迁完手动拖一次。

### Safari 的阅读列表能一起迁到 Chrome 吗？

不能，也没有等价的完整对应物。阅读列表是 Safari 独立于书签维护的「稍后读」队列，HTML 书签格式里没有位置放它。Chrome 侧的对应物是「稍后阅读」或第三方扩展，行为不完全一致。可靠做法是迁移前在 Safari 里把要留的文章手动存成普通书签。

### 智能文件夹怎么办？Chrome 里有对应功能吗？

没有对应概念。Safari 的智能文件夹是基于规则动态聚合的查询，不是静态清单，HTML 格式无法表达这种结构。迁移前展开需要的智能文件夹，全选后另存为普通文件夹，Chrome 里就有一个等价的静态版本了。

### 用同步工具能保持 Safari 和 Chrome 长期同步吗？

目前不行。BookmarkSync 支持 Chrome、Edge、Firefox，**Safari 暂时不支持**，没有 Safari 扩展。所以现阶段可行的组合是：用原生导入完成一次性搬家，之后靠 Chrome 侧同步在多台设备间保持一致；Safari 自己的那份靠 iCloud 在 Apple 生态内保持。跨浏览器持续同步的价值要在 Chrome、Edge、Firefox 之间才成立。

### 用 Apple ID 登录 Chrome 扩展，书签数据会经过谁？

iCloud 扩展这条路径下，书签数据经过 Apple 和 Google 两家。如果你想减少数据流转、或者不希望 iCloud 内容和 Google 账号关联，那就别用这个扩展，改走手动导出 HTML 再自己导入——这条路上书签只在你本机，不会主动上传。另外注意，Chrome 同步的加密范围有限：Google 官方明确说明支付方式和地址不受同步口令加密。
