# 文件夹改名后子项全丢：为什么会发生，以及怎么避免

给文件夹改个名字，里面收藏了几百条的子书签就没了。或者把文件夹拖到另一个位置，它整层内容跟着「蒸发」。这不是你操作错了，也不是浏览器 bug——是同步机制在按一种有缺陷的方式工作。

## 根因：书签被存成了「路径字符串」

要看懂这个问题，先得知道一个多数同步工具不会告诉你的实现细节：同步引擎眼里，一个书签节点**到底是什么**。

有两种做法：

| 存储方式 | 一个书签实际是什么 | 父文件夹改名后 |
|---|---|---|
| **路径字符串** | `"用户书签/工作/工具/某个网站"` | 路径前缀变了 → 这个书签变成孤儿 → **消失** |
| **独立节点 + 父指针** | `{id: "n7", parentId: "f3", title: "某个网站"}` | 父节点只是换个 id，id 不变 → **完好无损** |

用路径字符串的方案，在同步时只能做「按路径比对两边一样不一样」。文件夹一改名，它看到的是「你这边有一堆东西不见了，那我就当被删了」，然后把删除同步到所有设备。于是你看到的不只是本地丢，是**全部设备一起丢**。

> 这也解释了为什么有些工具会「自己好了」：你把文件夹名字改回去，它又出现了。这类工具不是修好了，只是碰巧回到了字符串匹配的结果。

## 正确的做法：同步节点身份，不同步路径

BookmarkSync 按第二种方式做。具体来说是三条：

1. **每个书签和文件夹有独立 ID**，同步的是 ID 之间的关系（`parentId`），不是它在哪条路径下。
2. **改名只改 `title` 字段**，不改任何 ID，也不改父子关系。所以改名对同步引擎来说根本不是「移动」，只是一次属性更新。
3. **移动文件夹改的是子节点的 `parentId`**，子节点自身的 ID 不变。100 条子书签各自还在，只是挂到了新父亲下面。

结果就是你期待的：改名和移动都只是「位置变了」，内容一条不少。

### 一条判据，你自己就能验证

打开任意一个同步工具，随便挑一个**有子项的文件夹**，改名然后刷新：

- 子书签全没了 → 它存的是路径字符串
- 子书签都在，顺序也保持 → 它存的是节点身份

这一步比读任何文档都快，也比任何宣传都可靠。

## 三种常见方案的实际情况

### 浏览器自带同步

Chrome 和 Edge 的原生同步对书签**移动和改名是安全的**，因为它们连整个浏览器配置档一起同步，本质上不存在「只同步书签树」的结构性问题。

它的问题在别处：书签以明文存在厂商的云里（除非你手动设了同步口令）、换浏览器就用不了、和其他浏览器完全不通。如果你的诉求是「浏览器之间互通」，原生同步解决不了。

### 通过导出 HTML 文件迁移

看起来最通用，但有一个隐蔽的坑：**HTML 书签文件不保存文件夹结构里那些「空的文件夹」和「只有子文件夹没有书签」的层级**。导入到另一个浏览器后你会发现某些嵌套层级被拍平了，或者多出一些你以为不存在的空目录。

而且这个过程完全手动——每次换设备都要重来一遍，中间任何一步点错都不可恢复。

### 文件级同步（网盘 / Git / WebDAV）

这类方案（把自己浏览器资料目录放进网盘同步）能保住完整结构，因为它就是复制文件。但代价是：**没有多设备合并能力**。两台设备离线各自改了同一个文件夹，同步时按文件时间戳决定谁赢 —— 你在 A 电脑加的 3 条书签会被 B 电脑的旧版本整份盖掉。

要安全就得手动锁文件，而这恰好把「自动同步」的意义抵消了。

## 该怎么选

| 你的诉求 | 合适的方案 |
|---|---|
| 只在 Chrome 内部用，机器之间搬一下 | 原生同步够用 |
| **浏览器之间互通，且结构不能坏** | 需要按节点身份同步的方案 |
| 要给团队/多台设备用，且要求能自动合并 | 同上，且必须支持冲突合并 |
| 想完全自己掌控数据 | 文件级同步，但要接受没有合并 |

BookmarkSync 支持 Chrome / Edge / Firefox，按节点身份同步，默认端到端加密（服务器存的是密文，连我们也读不到你的书签内容）。免费档 1,000 条书签、1 个同步空间、3 台设备，够验证这套机制是不是你想要的。

## FAQ

### 文件夹改名后子项没了，还能恢复吗？

如果子项还在云端的其他设备上，通常能：先**停掉所有设备的同步**，避免删除继续传播，然后在任一仍保有完整副本的设备上操作。

更常见的做法是提前做一次导出备份——书签导出成 HTML 是一分钟的事，但它不能保住空的中间层文件夹，所以只当兜底，不当主力。

### 为什么有些工具改了名又改回来，东西就回来了？

因为它存的是路径字符串。改名那一刻路径失效，书签被判成「已删除」；改回去之后路径又匹配上了，看起来像「好了」。这是假象——这期间删除可能已经同步到别的设备了。

真正的判据是：这个工具在改名后，**书签的唯一标识有没有变**。变了就是路径方案，结构迟早会坏。

### 只移动文件夹位置、不改名，会有同样问题吗？

看实现。如果它同步的是路径，位置一变路径就变，一样会丢；如果同步的是节点身份，移动只是改父子关系，内容不会动。这两者的区别只有改一次文件夹名就能测出来。

### 自动整理工具（去重、归类）会不会破坏我的结构？

取决于它调用的接口行为。只做「移动」和「新建」的整理不会丢数据；会删文件夹的实现有风险——删除一旦被同步传播，就不只是本机的事了。我们做自动整理时也只移动、不删除，就是这个原因。

### 同步中的书签能安全地改名吗？

可以。改名是同步引擎最容易正确处理的操作，因为它只涉及一个节点自身的属性，不涉及任何其他节点的关系变化。

真正需要小心的是**移动**：它会改变一整棵子树的归属。如果某个实现把移动写成了「删除 + 新建」，那这一整棵子树就会以你意想不到的方式消失。
