# 三浏览器手工测试计划（Chrome / Edge / Firefox）

> 适用版本：v0.1.0 开发分支（快照 + 墓碑 + 三态合并引擎，多空间/多设备版）
> 约定：**A = Chrome，B = Edge，C = Firefox**，三端登录**同一个测试账号**。
> 同步没有书签变更监听——只在「扩展安装时 / 浏览器启动时 / 手动点击」触发，
> 所以**每一步改动之后，都必须回到扩展界面点「立即同步」**，这是本测试的基本节奏。

---

## 0. 环境准备（套件 A）

### A1. 构建产物

```bash
pnpm install            # 如果还没装依赖
npx vite build          # → extension/   （Chrome 和 Edge 用这份）
node scripts/build-firefox.mjs   # → extension-firefox/（Firefox 用这份）
```

注意：**不要用 `pnpm build`**（会附带跑 Safari 后处理脚本）。

### A2. 三端加载扩展

| 浏览器      | 加载方式                                                                         | 目标目录                                  |
| ----------- | -------------------------------------------------------------------------------- | ----------------------------------------- |
| A = Chrome  | `chrome://extensions` → 开启「开发者模式」→「加载已解压的扩展程序」              | `extension/`                              |
| B = Edge    | `edge://extensions` → 开启「开发人员模式」→「加载解压缩的扩展」                  | `extension/`（可与 Chrome 同一份）        |
| C = Firefox | `about:debugging#/runtime/this-firefox` → 「临时载入附加组件」→ 选 manifest 文件 | `extension-firefox/manifest.firefox.json` |

Firefox 注意：**临时加载重启浏览器后失效**，需重新载入；重载后 `deviceId` 不变（存在 storage.local），但 **登录取决于 storage 是否保留**（about:debugging 重载不清 storage，重启浏览器后临时扩展整个消失，storage 一并丢失 → 之后每套件尽量别重启 Firefox；若必须重启，把 Firefox 的步骤集中在一次会话里做完）。

### A3. 账号与初始状态

- [ ] 准备 1 个测试邮箱（Supabase 注册可能需要收确认邮件：注册后若提示「注册成功，请查收确认邮件后登录」，先去邮箱确认）。
- [ ] 建议三个浏览器都用**干净/空书签**的 profile（先手动备份/清空书签栏），排除浏览器自带书签干扰。
- [ ] A、B、C 依次登录同一账号。登录入口：点扩展图标弹出的 popup，或右键图标 → 选项（options 页，推荐用 options 页，窗口稳定不中断长同步）。

### A4. 每端先设置设备名

登录后 → 「空间 / 设备」→ 底部输入框填「本设备显示名称」→ 保存名称：

- [ ] A 填 `Chrome-测试机`，B 填 `Edge-测试机`，C 填 `Firefox-测试机`

### A5. 观察工具（排查问题时用）

| 看什么                              | 怎么看                                                                                                                                                                                                                                            |
| ----------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 同步状态行                          | 扩展 UI 底部灰字：`完成: 推送 N · 拉取 N` / 各种错误原因                                                                                                                                                                                          |
| 后台日志                            | Chrome/Edge：`chrome://extensions` → Bookmark Sync → 点「Service Worker」；Firefox：`about:debugging` → Bookmark Sync → 「检查」                                                                                                                  |
| 本地存储（映射/基线/墓碑/确认标记） | options 页 F12 控制台执行 `chrome.storage.local.get(null, console.log)`（Firefox 用 `browser.storage.local.get().then(console.log)`）；关注 `deviceId`、`activeSpaceId`、`mergeAck:<uid>`、`lastSyncBaseline*`、`syncIdMaps*`、`localTombstones*` |
| 远端数据                            | 可用只读 MCP `list_tables` / SELECT `bsync_snapshots`、`bsync_devices`、`bsync_spaces`（不要写）                                                                                                                                                  |

### A6. 首次同步 + 多设备合并确认弹窗

前置：A 先点「立即同步」完成一次（空树 → 推送 N · 拉取 0）。

1. [ ] B 点「立即同步」→ **预期弹出「此账号已在其他设备上同步」确认框**，列出 Chrome-测试机的名字和上次同步时间。
2. [ ] 先点「先不同步」→ 状态显示「检测到其他设备正在使用此账号…」，数据未合并。
3. [ ] 再点「立即同步」→ 弹窗再现 → 点「我知道了，合并同步」→ 同步放行，状态 `完成: 推送 N · 拉取 N`。
4. [ ] C（Firefox）点「立即同步」→ 因为 A、B 都活跃，同样应弹确认框 → 确认后放行。
5. [ ] 此后 A/B/C 再点「立即同步」不应再弹（本机已记 `mergeAck:<uid>`）。
   > 重测技巧：想再触发弹窗，在控制台找到 `mergeAck:` 开头的键删掉即可。

**记录**：弹窗文案里列出的设备名是否正确；确认后三端「空间 / 设备」列表是否都出现 3 台设备。

## 1. 套件 B：基础新增同步 + 根目录映射（核心路径）

### B1. 建立标准夹具（A 端操作）

在 Chrome 书签栏（Ctrl+Shift+O 打开书签管理器）建：

```
书签栏
├── 前端手册/            （文件夹）
│   ├── GitHub     https://github.com
│   └── MDN        https://developer.mozilla.org/zh-CN/
├── 日常/               （文件夹）
│   ├── 知乎        https://www.zhihu.com
│   └── Bilibili   https://www.bilibili.com
└── Supabase       https://supabase.com      （书签栏直下）
```

- [ ] A 点「立即同步」→ 状态 `完成: 推送 N · 拉取 0`（推送数 ≈ 全部节点数属正常，本引擎是全量推送模型）。

### B2. 传播到 B、C

- [ ] B「立即同步」→ **预期**：书签栏出现「前端手册」「日常」「Supabase」，结构、顺序与 A 一致。
- [ ] C「立即同步」→ 记录落点（见下方 ★ 观察点）。
- [ ] 三端再各点一次「立即同步」→ **预期**第二次 `推送 N · 拉取 0` 且无任何变化（幂等）。

### B3. 反向新增（C 端 → 全网）

- [ ] C 在 Firefox **书签工具栏**新建书签：`Hacker News` → `https://news.ycombinator.com` → C 同步。
- [ ] B 同步 → A 同步 → **预期**：两端都出现 Hacker News。
- [ ] **记录它落在 A/B 的哪个根目录**（书签栏 or 其他书签）。

### B4. ★ 根目录映射观察点（疑似 bug，请重点记录）

代码设计意图是：Chrome 书签栏 ↔ Firefox 书签工具栏，Chrome 其他书签 ↔ Firefox 书签菜单。
但 `readLocalTree` 和 `applyNodes` 对 Firefox 根的判定**不一致**（读取时把「书签工具栏」当 `__bar__`、
「书签菜单」当 `__other__`；写回时却把 `__bar__` 写到 `roots[0]`，而 Firefox 的 `roots[0]` 是「书签菜单」）。

按代码推演的**预测行为**（请逐条对照实测）：

1. [ ] B2 中 C 拉到的「前端手册/日常/Supabase」预计**先落在 Firefox 的「书签菜单」**而不是书签工具栏。
2. [ ] C **再同步一次**：这些条目预计从「书签菜单」**迁移到「书签工具栏」**（并集模型下父目录变化视为本地修改）。
3. [ ] 然后再同步 A：Chrome 书签栏里这批条目预计**迁移到「其他书签」**（远端父目录已被 C 改成 `__other__`）。
4. [ ] Firefox 放在「其他书签」（unfiled）里的书签预计**完全不参与同步**（读取范围只覆盖工具栏+菜单）。

> 如果实测与预测一致 → 确认存在跨端根目录迁移 bug，值得修复；如果实测三端稳定在「书签栏 ↔ 工具栏」对齐，说明我对 Firefox 根顺序的推演有误，请记录实际映射关系即可。无论哪种结果，把三端实际落点画个对照表。

- [ ] A 把「Supabase」拖进「前端手册」文件夹 → A 同步 → B、C 同步 → 三端位置一致（都在「前端手册」内），原位置无残留。

## 3. 套件 D：删除与墓碑（粘性删除，协议核心）

前置：套件 C 完成，三端基线一致（可先各同步一次）。

### D1. 基本删除传播

- [ ] A 删除「GitHub」→ A 同步 → B 同步（GitHub 消失）→ C 同步（GitHub 消失）。
- [ ] 三端再各同步一次 → GitHub 不复活（墓碑不失效）。

### D2. 一端删、另一端改（删除获胜）

1. [ ] C **先离线修改**「MDN」标题为「MDN-离线改」（不同步）。
2. [ ] A 删除「MDN」→ A 同步 → B 同步（MDN 消失）。
3. [ ] C 此时同步 → **预期**：删除获胜——C 上那条「MDN-离线改」也被删掉（墓碑粘性 + 本地三态双保险）。记录实测。

### D3. 删除端重加（原删除设备获胜，预测：重加被吞）

- [ ] 在 **A（删除过 GitHub 的设备）** 重新添加 `GitHub → https://github.com`（同名同 URL 同位置）→ A 同步。
- [ ] **按代码预测**：重加会被身份对齐回原 sync_id，被服务端墓碑过滤 → 不会出现；并且之后再同步一两次，这条重加甚至会从 A 本地被清掉。
- [ ] 实测记录 A 本地最终状态。

### D4. 非删除端重加（并集保留，预测：以新节点复活）

- [ ] 在 **B（从未删过 GitHub 的设备）** 重新添加同内容书签 → B 同步 → **预测**：作为「新增节点」（新 sync_id）重新出现在全网。
- [ ] A、C 同步 → 三端都出现这条 GitHub → 记录：是否出现**双份**（若 A 本地 D3 的重加还残留着，可能与 B 的重加并存成两条同 URL 书签）。
- [ ] 记录最终三端 GitHub 的数量（0 / 1 / 2 条）。

## 4. 套件 E：多空间（工作空间）

> 空间模型先说清楚，避免误判为 bug：**本地书签树只有一棵**，「空间」是服务端的多棵独立树。
> 切换空间后同步 = 把本机当前整棵树**并集并入**该空间（UI 提示原文：「本设备书签会并入该空间」）。

前置：套件 D 完成；记录此刻默认空间的完整书签清单。

### E1. 创建与切换

- [ ] A →「空间 / 设备」→ 输入「工作」→ 创建 → 列表出现「工作」和「默认空间」。
- [ ] 点击「工作」名称 → 高亮切换 → 状态提示「已切换到空间「工作」…」。
- [ ] A 新增书签：`公司Wiki → https://wiki.example.com`（example 域名，避免误点）→ A 同步。
- [ ] **预期**：推送数 ≈ 本机全部节点（整树并入），状态行尾部显示 `· 空间: 工作`。

### E2. 空间隔离观察

- [ ] B **不切空间**直接同步 → **预期**：B 的默认空间拉不到「公司Wiki」（记录是否真的隔离）。
- [ ] B 切到「工作」→ 同步 → **预期**：「公司Wiki」出现；同时 B 的整棵树也并入了「工作」空间（推送数大）。
- [ ] **记录**：此时打开 A 或 B 的「历史记录」（列表按当前空间过滤），观察「工作」空间的快照是否包含默认空间的书签副本（这是设计行为，确认文案与行为一致即可）。

### E3. 切回默认（观察是否跨空间污染）

- [ ] B 切回「默认空间」→ 同步 → **预测**：因为 B 本地树里已有「公司Wiki」（且默认空间基线里没有），它会被当作本地新增**推入默认空间** —— 即工作书签泄漏到默认空间。记录实测（若如此，属于「切空间合并模型」的已知副作用，可评估是否要改为隔离式）。

### E4. 改名 / 删除 / 上限

- [ ] A 在空间列表把「工作」改名「公司」→ 成功；C 端打开空间列表（或重新打开面板）看到新名。
- [ ] A 删除「公司」→ confirm 弹窗 → 删除成功；若 B 的 `activeSpaceId` 指向它，B 下次打开面板/同步应回退到默认空间（记录）。
- [ ] 尝试删除「默认空间」→ **预期**：拒绝，提示「默认空间不可删除」。
- [ ] Free 档位再建第二个空间 → **预期**：弹升级 modal，提示「空间数量已达当前档位上限」（Free 1 个 · Plus 3 个 · Pro 10 个）。

## 8. 套件 I：AI 功能验收（BYOK / 整理 / 体检 / 健康 / 问答 / 地址栏）

> 前置：A/B/C 任一浏览器已登录、已完成过至少一次同步（套件 A~D 的夹具书签在本地即可）。
> 本套件**只需要一台浏览器**做完（建议 A = Chrome），除非某步明确要跨端。
> 需要一个真实可用的 API Key（DeepSeek / OpenAI / Anthropic 任一，或本地 `ollama serve`）。
> 决策与实现的来龙去脉见 `docs/design/ai-features.md`，本节只验「跑起来对不对」。

### I1. 首次配置 provider + key（设置页 → 第 1 个 pane「AI」）

- [ ] 打开设置页 → 「AI」pane → **预期**：列表为空，显示「还没有添加任何模型」，总开关处于**关闭**状态。
- [ ] 点「添加模型」→ 选 DeepSeek → **预期**：直接进第二步编辑弹窗，`接口地址` 预填 `https://api.deepseek.com`、`模型` 预填 `deepseek-v4-flash`（旧名 `deepseek-chat` 已弃用，填它会 400）。

- [ ] 打开 `chrome://settings` 之外确认**没有**任何 `storage.sync` 写入：控制台执行 `chrome.storage.sync.get(null, console.log)` → **预期**：输出里**没有** `ai.*` 任何键（key 不漫游）。

### I6. 链接体检（授权前后 broken vs unknown 的差别，核心对照步骤）

夹具：在「待整理」旁加一条必然 404 的书签，如 `Dead → https://example.org/definitely-not-a-real-page-20261018`。

**先测「未授权」的降级表现**（若 I2 已授权过，先在扩展页收回 host 权限）：

- [ ] 「链接体检」→ **预期**：直接进 unauthorized 态，说明「没有 host 权限时跨域请求返回 opaque 响应 —— 404 和正常页面无法区分」，给出「授权」按钮 + 三条说明（仅发一次请求 / 不读不存页面内容 / 随时可收回）。
- [ ] 不授权硬跑（若界面允许）→ **预期**：几乎所有站点落进 **unknown**，`broken` 数为 0 或极少 → 记录对照数字。★ 这就是「未授权时探活等于白跑」。

**授权后**：

- [ ] 点「授权」→ 同意两条通配 host 权限 → **预期**：进入 idle 态，显示检测范围「全部书签（N）」与「开始检测」，并写明「检测在本页运行 —— 请保持标签页打开，关掉即中止」。
- [ ] 点「开始检测」→ **预期**：进度逐条推进（串行、有明显间隔，不是并发齐发），中途可「暂停 / 继续 / 停止」。
- [ ] 看报告分类 → **预期**：- `Dead` 那条 = **broken**（404）- github.com / MDN 等 = **ok** 或同站 **redirect** - 有域名迁移的（如 `https://v3.vuejs.org` 这类）= **changed**（跨 host）- 反爬站点（知乎/bilibili 常 403）= **unknown**，且界面**不把它当失效**
      ★ 核心判据：**unknown 与 broken 必须分开显示、数字不同**。若 unknown 被并进「失效」，护栏失效。
- [ ] 关掉该标签页 → 重开 → **预期**：检测中止、进度丢失（不报错），需要重跑。
- [ ] 若有配 AI：跑一次「获取修复建议」→ **预期**：只对 broken 项给建议，unknown 项不参与；没把握的项宁可不给（不是每条都编一个新地址）。
- [ ] 勾选一条建议 → 点「应用修复」→ **预期**：需**两步确认**（第一次点进入倒计时 armed 态，3 秒内再点才执行）→ 书签 **URL 被改掉，书签本身仍在**（★ 不删节点）。
- [ ] 点「撤销」→ **预期**：URL 写回旧值，书签不消失。切页/关标签后撤销不可用（内存快照），属预期。
- [ ] B 端同步 → **预期**：三端 URL 一致，无新增删除记录（可在 B 端确认书签数量未变）。

### I7. 健康洞察（沉睡口径 + 只有数字出本机）

- [ ] 「健康洞察」→ **预期**：四张卡：沉睡书签 / 重复书签 / 空文件夹 / 失效链接；数字来自本机统计。

- [ ] ★ 打开 F12 Network，抓这条 AI 请求的**请求体** → **预期**：里面只有几个数字（total / loose / duplicateGroups / emptyFolders / sleeping / broken 之类），**不含任何书签标题或 URL**。这是本模块最重要的一条约束，值得手验一次。
- [ ] 生成中再点一次 → **预期**：变成「停止」（中止，不当失败报错）。
- [ ] 「整理建议」区 → 点「去归类」/「去检测」→ **预期**：跳到对应 pane（整理书签 / 链接体检），不是开新标签。
- [ ] 关掉 AI 总开关后进健康洞察 → **预期**：AI 按钮**禁用并说明原因**，统计卡片照常显示（统计不依赖 AI）。

## 附录 2：已知/疑似问题清单（测试时优先验证）

1. **Firefox 根目录映射疑似 bug**（套件 B4）：读取侧与写回侧对 Firefox 根的判定不一致，预测会出现「书签栏内容在 Firefox 落到书签菜单 → 下一轮迁到工具栏 → 再把 Chrome 端拖去其他书签」的链式迁移。
2. **Firefox「其他书签」不参与同步**（套件 B4-4）：读取范围只覆盖工具栏 + 菜单。
3. **空间切换的并集副作用**（套件 E3）：本地树只有一棵，切空间+同步会把整树并入目标空间，切回默认时可能把目标空间的书签带回来。
4. **推送数恒等于全量节点数**：状态行「推送 N」不是增量数，容易误读，确认文案是否需要改进。
5. **AI 套件的「预期」里有几条是设计上的限制，测出来像 bug 但不是**：撤销按钮在切页/关标签后消失（快照只在内存）、地址栏未选中建议时回车无反应（刻意不外发）、health 卡「--」而非 0（口径取不到与取到 0 是两件事）、未授权 host 权限时链接体检几乎全是 unknown。逐条理由见 `docs/design/ai-features.md` 第 6 节「已知限制」，**不要**照着这份清单去改代码。
